GLFS Advisories

This page covers advisories, notably in relation with security and changes that may have broken earlier versions of the book.

For security, most of the packages in GLFS are in BLFS, and GLFS for the most part gets the same updates as BLFS gets. Thus, you should check the BLFS advisories linked in each section. This page covers GLFS-specific issues, or when the BLFS issues hit GLFS the hardest.

This page is ordered like the Changelog of the book, with newest items first.


13.0 to 13.1

Broken changes

Packages removed from GLFS that are in BLFS may have gotten security updates. Read BLFS 13.0 Security Advisories and BLFS Consolidated Security Advisories for such packages.

glfs-brk-13.0-001: OpenCL and Ruby (Date: May 29th, 2026)

GLFS used to install OCL-ICD from OCL-Dev as the OpenCL ICD loader. This in turn required Ruby, and Ruby was only required for that package. KhronosGroup has a compatible open source loader, called OpenCL-ICD-Loader, which at the moment of this being issued is at OpenCL API version 3. The only dependencies it requires are CMake and the OpenCL headers.

As a result, OCL-ICD has been removed in favor of this compatible ICD loader, which is now part of a page called "OpenCL-SDK". The OpenCL-SDK page used to be called "OpenCL-Headers", but now everything is provided all at once. All the packages in it are at the same version. Ruby has also been removed since it is no longer needed in GLFS, although it has more applications in and out of BLFS. Ruby is a BLFS package, and often has security updates. You can update Ruby from the BLFS Ruby page. OCL-ICD was a GLFS-specific package. BLFS does not provide traditional OpenCL support besides libclc for Mesa, but Mesa does not provide an OpenCL ICD in BLFS unless an ICD loader is present and you opt-in to RustICL (RustICL is not enabled by default). Migrating from OCL-ICD to the complete KronosGroup OpenCL-SDK is safe, and recommended as it provides CMake Find Modules for OpenCL so that CMake projects can do a standard check for OpenCL without Pkg-Config.

glfs-sa-13.0-001: NVIDIA-r580 - Rating: High (Date: March 21st, 2026)

In NVIDIA-580.142, one security vulnerability was fixed that could allow for a denial of service attack via a kernel crash by exploiting a NULL pointer dereference. This issue affects the kernel-open kernel modules in a file called kernel-open/common/displayport/src/dp_connectorimpl.cpp. Despite the kernel modules being open, everything in kernel-open/common is precompiled in the kernel-open/nvidia/nv-kernel.o_binary object relocatable. It can be compiled by installing open-gpu-kernel-modules, not in GLFS currently. This issue has no CVE or any ID with security authority. The pull request for the issue can be found at open-gpu-kernel-modules#1040.

Update to NVIDIA-580.142 or a later r580 version by following the GLFS NVIDIA-r580 installation page. Ensure you download the latest install script and manifest file if you previously downloaded them to ensure compatibility.

Broken changes

Packages removed from GLFS that are in BLFS may have gotten security updates. Read BLFS 12.4 Security Advisories and BLFS Consolidated Security Advisories for such packages.

glfs-brk-12.4-006: Pkgconf and Meson (Date: February 24th, 2026)

GLFS previously installed files for Pkgconf and Meson to help aid with targetting 32-bit on 64-bit. After attempting to upgrade lib32-Systemd in MLFS, it revealed that it pulled in libraries that were only built for 64-bit which led to linker errors. It made sense to move those files to MLFS to make installing and upgrading a more reliable process. The files for Meson in particular now include the --libdir=$PREFIX/lib32 option and GLFS now relies on it. There are warnings on each page that uses Meson cross files about this. For Pkgconf, the files can be installed from the MLFS Pkgconf page. For Meson, the files can be installed from the MLFS Meson page.

glfs-brk-12.4-005: NVIDIA (Date: December 23rd, 2025)

NVIDIA released major version r590 which dropped support for pre-Turing NVIDIA cards. GLFS now includes two versions of NVIDIA (as well as CUDA) to provide support for pre and post Turing GPUs. You must now decide which version to install from. You should read NVIDIA Revisions to get an idea of what to install. If you have https://linuxfromscratch.org/glfs/view/dev/shareddeps/nvidia.html bookmarked and use it to install NVIDIA, you should be careful installing the package to avoid losing support for your GPU.

glfs-brk-12.4-004: VDPAU (Date: November 24th, 2025)

VDPAU support has been cut in Mesa-25.3.x, removing most of the VDPAU drivers out there. The main reason for this is that the benefits of VDPAU are minor and is restricted to X11 only. It has been superceded by VA-API which is window-system independent and offers more benefits. It is a logical step to cut VDPAU, given how most of the drivers are now gone. However, NVIDIA technically has a VDPAU driver, but no VA-API driver in the NVIDIA runfile. There is a VA-API NVIDIA driver in a separate package (NVIDIA-VA-API-Driver) that provides decoding support for multiple codecs and has been added to GLFS. It uses NVDEC as the backend without requiring the CUDA NVCC compiler, leading to a simple installation. Because of this, and how most GPUs have a VA-API driver, VDPAU support has been cut in general from GLFS. This means the libvdpau and libvdpau-va-gl packages are no longer offered in the book and VA-API is preferred. For NVIDIA, CUDA is still offered in SLFS for packages that want explicit control, like FFmpeg and OBS-Studio, and will not be axed anytime soon. Part of this overall change is that nv-codec-headers (ffnvcodec) has been moved from SLFS into GLFS to satisfy a dependency for NVIDIA-VA-API-Driver. In any case, it was decided that users will want to install nv-codec-headers (ffnvcodec) anyway for a plethora of reasons.

glfs-brk-12.4-003: GBM (Date: September 11th, 2025)

GLFS provides instructions to install libgbm, a frontend that loads a given backend. This avoids having to install Mesa if a user is installing a driver outside it that provides nearly everything that's needed. This library was installed from the Mesa project, finetuned to install the least amount of files possible. GLFS has since switched to installing the libgbm package outside of Mesa. It's a package that was ripped out of Mesa to avoid unneeded dependencies, build targets, and build time. The installation of certain header files, like for declaring the DRI interface needed by Xorg-Server, has been moved to pages installing drivers outside of Mesa, like NVIDIA. As with GBM from Mesa, you can pick between libgbm or Mesa without consequence. libgbm can replace Mesa's libgbm with no issues, being ABI compatible.

glfs-brk-12.4-002: Mesa OpenGL (Date: September 8th, 2025)

GLFS used to support Mesa's core OpenGL libraries (libGL, libEGL, etc.) and equipped the user with the information needed to go with any given core OpenGL library vendor. To a degree, GLFS still does; however, Mesa as a core OpenGL library vendor is no longer supported in the book. It instead prefers libglvnd and its instructions are designed to now funnel the user into using it. It still equips the user with information needed to use Mesa as the core OpenGL library vendor, and the issues that might arise. Mesa as an OpenGL and other API driver vendor is still supported as most drivers on Linux come from the project. However, libGL and other libraries of its ilk are now provided by libglvnd.

glfs-brk-12.4-001: PCRE2, SQLite3, Python3 (Date: September 4th, 2025)

PCRE2, SQLite3, and Python3 have been removed from GLFS. All of them are now in Multilib LFS and have proper lib32 instructions if applicable. Go to MLFS for updates to those packages.

glfs-sa-12.4-003: FFmpeg - Rating: High (Date: December 4th, 2025)

In FFmpeg-8.0.1, a security vulnerability was fixed that could allow for use-after-free write operations. This issue will not be fixed in FFmpeg-7.1.x. This vulnerability has been assigned CVE-2025-59734. The issue can be triggered by multiple games, including LucasArts games. Only an upgrade to FFmpeg-8.0.1 will fix the issue, but it breaks ABI and API.

To upgrade to FFmpeg-8.0.1, follow the FFmpeg installation page. SysVinit and Systemd instructions don't differ for that page.

glfs-sa-12.4-002: FFmpeg - Rating: High (Date: December 4th, 2025)

In FFmpeg-7.1.3, two security vulnerabilities were fixed that could allow for out-of-bounds write operations and integer overflows. These issues are fixed in FFmpeg-8.0.1. These security vulnerabilities have been assigned CVE-2025-59733 and CVE-2025-63757.

There is another vulnerability that most likely will not be fixed in FFmpeg-7.1.x because the fixes required cannot be backported easily. It allows for use-after-free write operations, and has a High rating. That vulnerability has been assigned CVE-2025-59734. The issue can be triggered by multiple games, including LucasArts games. Only an upgrade to FFmpeg-8.0.1 will fix the issue, but it breaks ABI and API.

Until most packages in BLFS and all of the packages in GLFS+SLFS are tested and adapted, GLFS will keep FFmpeg at version 7.1.x. The installation page for FFmpeg covers how to upgrade to version 8.0.1 to solve that vulnerability.

To upgrade to FFmpeg-7.1.3 (or FFmpeg-8.0.1), follow the FFmpeg installation page. SysVinit and Systemd instructions don't differ for that page.

12.3 to 12.4

Broken changes

Packages removed from GLFS that are in BLFS may have gotten security updates. Read BLFS 12.3 Security Advisories and BLFS Consolidated Security Advisories for such packages.

glfs-brk-12.3-007: xcb-util-errors (Date: August 17th, 2025)

xcb-util-errors has been removed from the XCB Utils page in GLFS and has been moved to Supplemental LFS. No packages in GLFS use xcb-util-errors. Originally, much like seatd, it was added in a time when SLFS (originally LFS-QOL) did not exist. But now it exists to offload such packages. So it got moved. You can read installation instructions for it here: xcb-util-errors. The page does not differ for Systemd.

glfs-brk-12.3-006: AMDGPU PRO (Date: July 18th, 2025)

Following the AMDGPU PRO deprecation announcement, dated 2025/05/31 at GLFS News, AMDGPU PRO has been removed from GLFS and there are no plans for it to return. Replace the AMDGPU PRO stack with libva, libvdpau, and Mesa.

glfs-brk-12.3-005: seatd (Date: June 10th, 2025)

seatd has been removed from GLFS and has been moved to Supplemental LFS. No packages in GLFS use seatd. Originally, it was added in a time when SLFS (originally LFS-QOL) did not exist. But now it exists to offload such packages. So it got moved. You can read installation instructions for it here: seatd.

glfs-brk-12.3-004: Git (Date: June 10th, 2025)

Git has been removed from GLFS. All downloading instructions now rely on the wget package when pages instruct the user to download files in bulk. No package in GLFS depends on Git otherwise, and no lib32 installation instructions have been present for it as the package does not provide libraries. Follow BLFS for updates to Git.

glfs-brk-12.3-003: libxml2 (Date: April 3rd, 2025)

libxml2-2.13 has upgraded to libxml2-2.14, which has broken ABI. While you can reinstall every package that uses libxml2, or do a complete upgrade, you can instead opt to apply patches which fix security issues without breaking ABI. The patches will be linked in the BLFS advisories.

glfs-brk-12.3-002: 32-bit CPU Support (Date: March 25th, 2025)

Support for 32-bit CPUs (ix86) has been removed from GLFS. This is because there is no testing being done for 32-bit by the GLFS development team due to lack of proper hardware. Another big reason is Steam and its CEF sandboxing is unclear on how to properly bypass and what happens beyond that point. Regardless, beyond Steam, the normal installation instructions generally work on 32-bit hardware; you just will be on your own to work around the edge cases.

glfs-brk-12.3-001: luit (Date: March 5th, 2025)

The luit package has been removed from GLFS as no packages in the book used it. It had no lib32 installation instructions, so feel free to follow BLFS for updates to the luit package.

glfs-sa-12.3-003: Fontconfig - Rating: Medium (Date: July 3rd, 2025)

In Fontconfig-2.17.1, a heap buffer overflow was fixed that was introduced in 2.17.0. When compiled with santized addresses, it will cause fc-cache to bail out when using the -f option when regenerating the font cache. If a font is malformed as a result of this early bail, Steam will crash, which is why it is mentioned in this advisories page. Upstream has not treated it as a security vulnerability and thus have not reserved a CVE or any security ticket with any authority. Since it can affect GLFS users directly and other issues of its ilk are considered security vulnerabilities, we consider this a vulnerability as well. This issue may not harm you, but if you are on Fontconfig-2.17.0, you should consider updating to Fontconfig-2.17.1 to avoid font recaching bailing via fc-cache which can cause Steam to crash. This is not needed for the 2.16 series.

To upgrade to Fontconfig-2.17.1, follow the GLFS Fontconfig installation page which does not differ for SysVinit/Systemd versions of the book.

glfs-sa-12.3-002: NVIDIA - Rating: High (Date: June 21st, 2025)

In NVIDIA-575.64, a security vulnerability was fixed that could allow for a use-after-free in the kernel for pre-Turing NVIDIA GPUs. NVIDIA has not reserved a CVE for the vulnerability. Furthermore, it has became clear that NVIDIA does not often document security fixes in the changelogs of the NVIDIA drivers, leading to many security fixes being unnoticed by the GLFS development team. We will now be looking at the NVIDIA Product Security resource. Consider all previous drivers to have security vulnerabilities and update to NVIDIA-575.64 or any of the latest revisions of the other 3 latest major versions (570, 565, and 560) immediately.

To do so, follow the GLFS NVIDIA installation page. Ensure you download the latest install script and manifest file if you previously downloaded them to ensure compatibility.

glfs-sa-12.3-001: libxml2 and Wine - Rating: High (Date: June 21st, 2025)

BLFS SA 12.3 060 covers a vulnerability with libxml2-2.14.4. This vulnerability is not exploitable in many packages as it is only able to be used in the xmlBuildQName() function. However, one of the packages that does make use of that function is the Wine package. If you are using Wine, you should fix the vulnerability by doing one of two things: either upgrade libxml2 to 2.14.4, or reinstall libxml2-1.13.8 with a patch.

To upgrade to libxml2-2.14.4, follow the GLFS libxml2 installation page which does not differ for SysVinit/Systemd versions of the book.

To reinstall libxml2-2.13.8 with the patch, download this patch and apply it before configuration, then reinstall the package.
